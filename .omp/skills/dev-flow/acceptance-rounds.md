# Раунды приёмки и багфикса после основного цикла

> Схема едет вместе с пакетом (`skill://dev-flow/acceptance-rounds.md`) — своей копии в
> проекте может не быть. Правило `acceptance-rounds` держит краткие инварианты и ссылается
> сюда за полной схемой.

План с тикетами закрывает **основной цикл** (реализация → тесты → ревью → ship).
Приёмка оператором **итеративна**: замечания приходят не одним списком, а волнами, и каждая
волна может затрагивать уже смерженную работу. Этот документ фиксирует, как вести такие
волны, не ломая методологию dev-flow.

## Три потока замечаний — три разных механизма

| Замечание на | Механизм | Новый тикет? |
|---|---|---|
| дифф **текущего** незакоммиченного тикета (стадия `stop-before-commit`) | правки в том же worktree, тот же ран; при необходимости — инкрементальное ревью дельты | **Нет** — часть текущего рана |
| **смерженной** работе активного плана (код/доки тикетов уже в `main`) | новый тикет раунда приёмки в том же плане, отдельный `/ship`-ран | **Да** |
| работе **после архивации плана** (эксплуатация) | обычный багфикс-контракт: `mp-diagnose` / `mp-grill-with-docs` → новый план или файл-план → `/ship` | Новый план/тикет |

Правило-разделитель: **архивные тикеты не переоткрываются**. Изменение результата
заархивированного тикета после мержа документируется следующим тикетом — так сохраняется
traceability: видно, что и почему менялось post-приёмке.

## Тикет раунда приёмки

- Файл `docs/plans/<slug>/NN-acceptance-round-K.md` (`node_type: ticket`), `NN` — продолжение
  нумерации плана; `depends_on: [предыдущий раунд или последний тикет]`.
- **Замечания фиксируются списком до старта рана**: каждый пункт — пронумерованное
  «было / надо» + чекбокс приёмки. Знание живёт в тикете (KB), а не в истории чата: через
  день неформальные замечания теряются.
- План остаётся `status: active`, пока приёмка не сошлась; архивация плана — только после
  закрытия последнего раунда.

## Пакетирование: сколько замечаний на тикет

- **Однородные мелкие замечания — один тикет-пачка.** Гейты рана (прогоны, ревью) дороги;
  тривиальная правка не тянет на вертикальный срез.
- **Делить на два тикета только при разной природе проверки** — например «KB/документация»
  (валидация: `gitmark lint` / `index`) против «код» (валидация: прогоны). Разные приёмочные
  критерии — разные раны.
- **Не заводить тикет на каждое замечание** — ceremony без пользы.
- Предел дробления: один раунд = один `/ship`-ран = одно окно контекста.

## Гейты раунда не режутся

Раунд приёмки проходит dev-flow полностью, с поправкой на природу изменений:

1. worktree от `main`;
2. правки по списку замечаний тикета;
3. **регресс затронутых сценариев**, а не только целевых: фикс, меняющий общий механизм,
   роняет ранее зелёные сценарии;
4. независимое ревью **дельты замечаний** (инкрементально);
5. `stop-before-commit` по умолчанию;
6. после мержа — тикет раунда в `archived`.

## Практика сбора замечаний

Оператор ведёт приёмку итерациями: смотрит диф/результат → выносит замечания → агент
оформляет очередной `NN-acceptance-round-K` → `/ship` → следующий круг зрения на уже
исправленную базу. Чередование «показать — заметить — исправить» и есть итеративная приёмка;
каждый виток заканчивается заархивированным тикетом, а не «мелкой правкой поверх всего».
