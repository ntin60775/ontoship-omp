# Контракт: движок видит команды/навыки пакета и знает свою версию

## Порядок выполнения

- **После** `deploy-check-marketplace-paths`: общий файл `.omp/skills/kb-search/SKILL.md`
  (тикет 01 того плана меняет путь к движку, этот план — описание новых возможностей).
- **Не связан** с `payload-refs-undelivered-docs`: общих файлов нет, порядок обратим.
- **До** `kb-docs-vs-plugin-delivery`: в scope того плана входит
  `docs/services/gitmark-cli/README.md` — спецификация движка, которую меняет этот.

## Goal

У потребителя с плагинной установкой инвариант I7 и команда `inventory` перестают быть
вакуумными: реестр `docs/reference/commands.md` отражает фактически доступные команды и
навыки пакета, а `gitmark version` сообщает версию поставленного пакета, а не константу.

## Done

- **Корень пакета резолвится самоотносительно** — от расположения самого скрипта
  (`skills/kb-search/gitmark.py` → два уровня вверх): `<plugin>` в плагинной установке,
  `.omp` в плоской. Ни `installed_plugins.json`, ни путь кэша не читаются: user-scope
  установки живут в `~/.omp/plugins/node_modules/<плагин>`, куда проектный скан не смотрит,
  а кэш версионирован. Тот же механизм, что принят для `deploy-check.sh` — один на пакет.
- **Скан команд и навыков — объединение**: `<корень пакета>/commands|skills` ∪
  `<корень проекта>/.omp/commands|skills`, дедупликация по разрешённому пути; при совпадении
  имён проектная команда перекрывает пакетную (та же логика приоритета, что у провайдеров
  omp: нативный проектный 100 > плагинный 90).
- В потребителях (`sot-omp-marketplace`, `erp-demo`) `inventory --check` докладывает
  фактическое число команд и навыков (12 и 12) вместо «0 команд · 0 навыков», реестр
  `docs/reference/commands.md` заполняется таблицами и секциями `## /<команда>`, а
  `gitmark lint` (I7) ловит реальный рассинхрон, а не пустоту.
- **Версия читается из манифеста пакета**: в payload появляется `.omp/package.json`
  (прецедент — sibling-плагин `1c`, у которого манифест лежит в корне плагина);
  `gitmark version` читает его из корня пакета, фолбэк — прежняя константа `VERSION`;
  то же значение пишется в `meta` индекса.
- Манифест не влияет на установку и апгрейд: версию для upgrade задаёт запись каталога
  (проверено ранее — манифест внутри плагина установщик не читает). Следствие в план:
  bump манифеста — шаг релиза в репо-каталоге, вместе с bump `ref`.
- Плоские потребители (6 проектов) не деградируют: объединение даёт тот же результат
  (корень пакета и есть `.omp`), а `version` в этом репо начинает читать манифест.
- KB синхронизирован: описание `inventory`/`version` в доках движка приведено к новому
  поведению, `gitmark lint` чистый, индекс пересобран.

## Scope

- `.omp/skills/kb-search/gitmark.py` — корень пакета, скан объединением, I7, `version`.
- `.omp/package.json` — новый манифест пакета (версия).
- `.omp/skills/kb-search/SKILL.md` — описание новых возможностей.
- `docs/services/gitmark-cli/README.md` — спецификация поведения.
- `docs/plans/README.md`.

Вне scope: доставка reference-доков в payload — план `payload-refs-undelivered-docs`;
тег и bump `ref` в каталоге — репо-каталог; поведение I7 при отсутствии реестра — не
меняем (остаётся `ERR`).

## Constraints

- Только stdlib, без новых зависимостей.
- Фолбэк обязателен: если манифеста нет, `version` возвращает прежнюю константу;
  если каталогов пакета нет — скан ведёт себя как раньше (плоская раскладка).
- Реестр остаётся генерируемым: руками не правится ни в пакете, ни у потребителя.
- Путь кэша и `installed_plugins.json` в коде не используются: они версионированы и
  зависят от области установки.

## Context

Аудит 2026-09-14 (отчёт `.scratch/audit-plugin-install-2026-09-14.md`, вне KB):

- `gitmark.py:485-486` — `COMMANDS_DIR = ".omp/commands"`, `SKILLS_DIR = ".omp/skills"`;
  `_scan_commands`/`_scan_skills` (gitmark.py:495-520) читают их от корня проекта. В
  плагинной установке этих каталогов нет — скан возвращает пусто.
- Последствие: у потребителя `python3 skill://kb-search/gitmark.py inventory --check`
  печатает «✓ реестр синхронен (0 команд · 0 навыков)», а `docs/reference/commands.md`
  (30 строк, маркеры без содержимого, ни одной секции `## /<команда>`) сам сообщает, что
  перечислять нечего — инвариант I7 выполняется формально.
- `gitmark.py:34` — `VERSION = "0.1.0"`; `.omp/package.json` в пакете нет, поэтому
  `gitmark version` печатает `gitmark 0.1.0` и в потребителе с плагином 0.2.0, и в плоской
  установке; то же значение уходит в `meta` индекса (gitmark.py:226).
- Области установки (проверено на машине): project-scope — `<проект>/.omp/plugins/node_modules/<плагин>`
  (симлинк в кэш) + `.omp/plugins/installed_plugins.json`; user-scope —
  `~/.omp/plugins/node_modules/<плагин>` + `~/.omp/plugins/installed_plugins.json`
  (там же `"version"`). Проектный скан user-scope не видит — отсюда выбор самоотносительного
  корня.
- Тикет «версия из манифеста» из архивного плана `marketplace-delivery`
  (репо-каталог) в поставку 0.2.0 не попал.
